# M0.9-A — Commercial Lease Management Foundation

This document describes the Lease Management implementation, not confirmed requirements from the Oxford City Council OCC001059 tender. No local copy of that specification was found during this milestone.

## 1. Domain models

A domain model represents a business concept and the information and rules attached to it. Here, a `Lease` represents a commercial agreement; `LeaseParty` represents a party in that agreement; `LeaseUnit` links the agreement to a Registry Unit; and `LeaseAuditEvent` records a successful change. See [`models.py`](../../services/lease-management/app/models.py).

The design supports a lease with more than one Unit and multiple joint tenants. Party records belong to a lease in this first version; a shared organization-wide party directory is deferred.

## 2. Relational databases

A relational database stores information in tables. Each row represents one record, and columns describe its fields. Related information is connected with keys. This makes it possible to preserve consistency—for example, a party row cannot point to a lease from another organization.

## 3. Primary and foreign keys

A primary key identifies one row, such as `Lease.id`. A foreign key points to another row. Lease parties, Unit references, and audit events use a composite foreign key to `(lease_id, organization_id)`, which prevents a related row from being attached across organizations.

`LeaseUnit.unit_id` is intentionally not a foreign key: Unit records belong to the separate Property & Asset Registry database. Lease Management stores the Unit's organization-scoped ID and hierarchy path, then asks the Registry API to confirm it. This follows BOWERA's domain-owned database boundary.

## 4. Database migrations

A migration is a versioned description of schema changes. [`0001_lease_management_initial.py`](../../services/lease-management/migrations/versions/0001_lease_management_initial.py) creates the lease, party, Unit-reference, and audit tables with their indexes and constraints. The migration is reviewable and has not been applied to a production database.

## 5. Financial decimal precision

Binary floating-point cannot represent every decimal fraction exactly. Rent therefore enters through a decimal string, is parsed as Python `Decimal`, and is stored as SQL `NUMERIC(14, 2)`. For example, the response keeps the exact two-decimal representation:

```python
rent_amount=f"{Decimal(lease.rent_amount):.2f}"
```

The API rejects floating-point rent input and values with more than two fractional digits. Supported currencies are explicitly limited to GBP, EUR, and USD for this foundation.

## 6. API validation

[`schemas.py`](../../services/lease-management/app/schemas.py) validates input types and allowed values before the database is changed. For example, a lease term must have an expiry date on or after its start date, and a break date must fall within the lease term. A lease must include at least one landlord and one tenant. Database constraints repeat important invariants so invalid rows cannot be inserted through a different code path.

## 7. Authorization

The API does not trust the organization ID in the URL as proof of access. Each request sends the caller's bearer token and a workload credential to the existing Organization & Access service. That service verifies the caller's active organization membership and role. Active members can read; owners and admins can write. All lease database queries include the authorized organization ID.

The Property & Asset Registry independently confirms that every referenced Unit belongs to the requested organization and current hierarchy and is active. The service fails closed if that API cannot be reached. The deterministic authorization decision is the security boundary—not possession of a UUID.

## 8. Audit transactions

An audit event contains the authorized actor, the event type, changed field names, and a timestamp. It is inserted in the same database transaction as each lease change. If the lease or audit insert fails, the transaction is rolled back so the service cannot report a successful write without its corresponding audit event.

## 9. Why lease dates matter

Start, expiry, and break dates affect occupancy, renewal planning, and downstream risk analysis. They are stored as calendar dates rather than timestamps because these fields describe contract dates, not moments in a time zone. This milestone checks date consistency but does not automatically transition status or issue notices.

## 10. How Lease data can connect to BOWERA Intelligence

The deterministic Intelligence engine can later receive validated lease-expiry information from Lease Management through an authenticated service API or event contract. The dashboard must not infer a missing expiry date, and Lease Management must not directly query the Registry database. A future integration should define ownership, freshness, authorization, and failure behaviour before exposing real tenant data.

## Unit reference freshness and known race

Lease create, update, and read operations revalidate each Unit against the authenticated Registry API. Inactive, missing, cross-organization, or hierarchy-mismatched references are rejected; a stale reference discovered while reading an existing lease returns a conflict rather than presenting it as current. Before the Registry deactivates a Unit, it asks Lease Management whether a draft or active lease references it. A referenced Unit is not deactivated, and an unavailable Lease service blocks that status change. A stale lease can still be terminated to release the reference. The Registry has no Unit deletion API.

These are detection safeguards, not an atomic lock. A Unit could still change after Registry validation and before the lease transaction commits, or a concurrent lease creation could race the retirement check. Blocking that race requires a Registry-side reservation/retirement protocol (including idempotent compensation and reconciliation), which is deferred rather than falsely claiming a distributed transaction.

## Scope

Implemented: organization-scoped lease references; start, expiry, and optional break dates; limited status; decimal rent and currency; payment frequency; landlord, tenant, and guarantor parties; multiple Unit references; joint tenants; create/read/update; and transactional audit history.

Deferred: tenant payments, rent reviews and indexation, document storage, notices, global party records, lease list/search/pagination, event publication, automatic lifecycle transitions, and the Unit reservation/retirement coordination needed to eliminate concurrency races.

No locally available OCC001059 tender specification was reviewed. These are proposed BOWERA capabilities, not verified tender requirements.

## Mini-test: questions and answers

1. **Why does `LeaseUnit.unit_id` have no foreign key to the Registry database?**
   Because each microservice owns its database; cross-service integrity is checked through the authenticated Registry API.

2. **Why use `Decimal` and `NUMERIC(14, 2)` for rent?**
   They preserve exact decimal monetary values, unlike binary floating-point.

3. **What proves that a caller may access an organization?**
   A server-side decision from Organization & Access based on the caller's authenticated identity and active membership, not a URL identifier.

4. **Why is a lease write and its audit event one transaction?**
   So a failed write cannot leave an unaudited lease change, and a failed audit cannot leave a reported successful change.

5. **Does checking the Registry API make a Unit reference immutable during a lease write?**
   No. Revalidation detects stale references at access time, but an atomic reservation/retirement protocol is required to prevent concurrent changes.
