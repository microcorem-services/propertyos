# M0.9-B — Secure Commercial Lease Management Interface

This milestone adds a browser-based lease register and create, view, and edit
workflow. It uses the independent Lease Management API from M0.9-A. No tender
requirements are claimed here: no local OCC001059 tender specification was
available for review.

## How a controlled React form works

A React component describes the page. A controlled input receives its current
value from component state and reports edits through `onChange`. In
`bow-era-lease-workspace.tsx`, the rent input is controlled with
`values.rent_amount`; updating it changes state, which updates the displayed
value.

The form keeps rent as text. It checks the text for a positive decimal with at
most two decimal places and submits a decimal string such as `"12500.50"`.
It does not convert money to a floating-point number or add currency
calculations.

## Form state and validation

The lease editor keeps its fields, selected Unit references, legal parties,
validation messages, and saving state separately. For example, `units` is
`LeaseUnitReference[]` and `values.parties` is `LeasePartyInput[]`.

Client-side validation helps a user correct mistakes before submitting. It is
not a security boundary: a caller can bypass the browser. The Lease Management
API validates fields again with Pydantic and database constraints. It checks
dates, permitted status/currency/frequency values, party roles, and decimal
precision. Unit references are checked against the authenticated Property &
Asset Registry API before the Lease transaction is committed.

## Next.js BFF and authenticated service calls

The browser sends same-origin requests to `/api/leases`. The route handler in
`src/lib/auth/lease-handlers.ts` reads the existing server-side session cookie,
checks the stored access token and its expiry, and calls the configured Lease
Management URL. It does not return credentials to the browser. Write requests
also require the configured application origin and a same-origin Fetch Metadata
header when provided.

The Lease API performs server-side authorization for each read, create, and
update. It obtains its workload token through its existing workload identity
configuration when it calls Organization & Access and the Registry. The
organization ID in a URL is only a requested context; the API independently
checks the user's permission and scopes database queries to that organization.

The lease register request has a bounded page size, search and status filters,
and an allowlisted sort field. The database orders records consistently and
filters every query by `organization_id`; it does not load an organization's
entire register at once.

## Relationships and property selection

The form's Portfolio, Site, Building, and Unit controls call the existing
same-origin Registry BFF endpoints. Users choose named active Units from the
selected organization's hierarchy; they do not type database identifiers.
The Lease API validates ownership and active status again at write time.

The Lease database stores the Registry IDs as references, not as cross-service
foreign keys. This preserves service ownership while still validating
references at use time. As documented in M0.9-A, validation and commit are not
a distributed transaction, so a concurrent Unit retirement can still race a
Lease write. Reservation/retirement coordination is future work.

## Table, permissions, and API errors

TanStack Table renders the register with stable Lease IDs as row identities.
Search, status filtering, and pagination are applied by the bounded server
endpoint; supported sort fields are sent to the API. Create and edit controls
are shown only when the Lease service's authorization decisions grant those
operations. Writes are still reauthorized by the API, so a stale UI permission
cannot grant access.

The BFF validates returned organization identity and record shape, limits
response size, disables caching and redirects, and maps upstream failures to
generic responses. The browser client shows safe messages instead of raw
service or database details. A `409` indicates an existing-data conflict; a
`403` indicates the operation is not permitted.

## Legal and audit safeguards

The screen labels the data as user-entered administrative information that has
not been independently legally validated. Dates are displayed as recorded;
the UI does not infer renewal rights, validate break clauses, calculate
rent-review entitlements, determine statutory obligations, or create or send
legal notices.

The detail screen displays the audit events already returned by the Lease API.
Lease writes and their audit events are committed in the same database
transaction. The UI does not invent an audit trail or expose infrastructure
credentials.

## How data reaches PostgreSQL

1. A user selects existing Units and enters parties and lease terms.
2. The browser sends a same-origin JSON request to the Next.js BFF.
3. The BFF resolves the authenticated session and forwards the user's access
   token to the configured Lease API.
4. The Lease API reauthorizes the organization and validates each Unit through
   the Registry API.
5. The Lease API validates the request and writes the Lease, associated Units
   and parties, and audit event in its own PostgreSQL transaction.
6. The BFF validates the returned organization and response shape before the
   browser displays the result.

## Mini-test: questions and answers

1. **Why does the rent input remain a decimal string?**
   It preserves the user's exact decimal text for API validation and avoids
   binary floating-point rounding.

2. **Does the organization ID in the URL authorize a user?**
   No. The Lease API checks the authenticated user's Organization & Access
   decision on every operation.

3. **Why can browser code call `/api/leases` but not the internal Lease API
   directly?**
   The same-origin BFF uses the server-side session, limits and validates
   upstream traffic, and keeps internal service configuration out of browser
   code.

4. **What does the Unit selector validate, and what does the Lease API repeat?**
   The selector loads active hierarchy options through the Registry BFF; the
   Lease API independently validates organization ownership and Unit status
   before writing.

5. **Does a recorded expiry date establish renewal or notice obligations?**
   No. The interface displays user-entered dates and makes no legal conclusion
   or notice.
