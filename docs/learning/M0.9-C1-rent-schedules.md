# M0.9-C1 — Secure Rent Schedules

This milestone adds expected rent instalments to the existing Lease Management
service. It extends the current lease domain and database; it does not add a
second service or database.

## What a rent schedule represents

A rent schedule records an amount per scheduled instalment, a frequency, a
date range, a due day, and a draft or active state. Currency comes from the
parent Lease. For example, a lease with GBP currency might have a monthly
`base_rent` schedule for `"12500.50"` due on the 31st.

An instalment is an expected obligation record, not a payment, receipt, or
accounting entry. This milestone implements only the `base_rent` category.
It does not perform collection, reconciliation, rent review, or legal
calculations.

## How recurring dates are calculated

`app/rent_schedules.py` calculates dates using calendar arithmetic. It anchors
the frequency to the schedule commencement month, advances by one, three, or
twelve months, and clamps a due day to the last day in a shorter month:

```python
due_date = due_date_for_month(year, month, due_day)
```

For a due day of 31, a monthly sequence can include 30 April, 31 May, and 30
June. For an annual due day of 29 February, non-leap years use 28 February;
the sequence remains anchored and returns to 29 February in a leap year.
Dates are inclusive and generated due dates must fall inside both the
schedule range and Lease term.

The schedule records `manual_review_reasons` when the commencement is not on
a generated due date or the end does not align with the day before the next
due date. The system displays those flags and does not calculate a partial
amount. The fixed amount is preserved for each generated due date; users must
review boundary periods rather than treating this schedule as a prorated
calculation or legal conclusion.

## Database changes and relationships

Migration `0002_rent_schedules` adds:

- `rent_schedules`, related to a Lease using the Lease service's organization
  and lease identifiers.
- `rent_installments`, related to a schedule and unique by organization,
  schedule, and due date.
- Additional allowed audit event types for schedule creation, editing,
  activation, and repaired installment generation.

Amounts use PostgreSQL `NUMERIC(14, 2)` and Python `Decimal`. The browser
keeps amount input as text; the API rejects floating-point JSON values. Each
instalment stores the exact amount and currency snapshot used when generated.
Changing a Lease's currency is rejected while any rent schedule exists so
stored expected amounts cannot silently change meaning.

Schedule generation checks existing due dates before inserting missing rows.
The database uniqueness constraint is the final duplicate guard. Schedule
writes lock the owning Lease row before checking for overlapping active
schedules of the same charge category. Drafts may overlap; activation is
rejected if an active schedule overlaps. The lock serializes Lease service
schedule writes without a cross-service database constraint.

Active schedules are immutable. A changed fixed amount or frequency requires
a new schedule over a non-overlapping date range. Schedules cannot extend
beyond the recorded Lease expiry, and later Lease date edits cannot exclude
existing schedules.

## Authentication and authorization

Authentication identifies the caller: the existing Next.js session supplies
the user access token to the same-origin BFF. The browser does not store a
service credential or call the internal Lease API directly.

Authorization decides whether that authenticated caller may act in the
selected organization. The BFF resolves the server-side session and validates
upstream data. The Lease API independently requires the existing Lease
read/update permission and scopes database queries by organization and Lease.
The organization identifier in the URL is a requested scope, not proof of
access.

## How the API, BFF, and interface work together

1. The lease detail page calls the same-origin
   `/api/leases/{leaseId}/rent-schedules` BFF route.
2. The BFF forwards the session token server-to-server to the configured
   Lease Management API and validates the schedule response.
3. The API reauthorizes the organization, locks the Lease for writes, checks
   its date range and schedule overlaps, and writes schedule, expected
   instalments, and audit history in a database transaction.
4. The interface displays expected due dates, exact decimal amounts, currency,
   status, and any boundary-review warning.

Schedule creation, draft edits, activation, and any actual installment
generation are included in the parent Lease audit history. Repeated
generation requests do not duplicate due dates and do not create redundant
audit entries when nothing changed.

## Important scope decisions

- Only `base_rent` is available as a charge category in this milestone.
- The short-month rule is explicitly `clamp_to_month_end`.
- Boundary periods are flagged for manual review; no proration is inferred.
- Lease expiry bounds generated obligations, but the software does not decide
  whether a contractual obligation is legally due.
- Expected instalments remain `expected`; payment collection and accounting
  status are outside scope.
