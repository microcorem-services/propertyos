# M0.9-C2 Learning: Service Charges & Property Expenses

## What was added in this milestone

M0.9-C2 extends the existing Lease Management capability with two related but distinct domains:

1. **Service charges** (tenant-facing recurring obligations) implemented by extending existing schedule logic.
2. **Property expenses** (landlord-side cost records) implemented as a separate register.

This keeps recurring tenant charges and owner expenses clearly separated while sharing security and validation patterns.

---

## Service charges in this architecture

Service charges are represented using the existing recurring schedule model used for rent schedules, with explicit charge categorisation:

- `base_rent`
- `service_charge`
- `building_maintenance`
- `insurance_contribution`
- `shared_facilities`
- `other_property_charge`

Each schedule records:

- charge category
- human-readable description
- exact decimal amount per period
- lease currency
- payment frequency (`monthly`, `quarterly`, `annually`)
- schedule dates (`start_date`, `end_date`)
- due-day and short-month handling
- lifecycle status (`draft`, `active`)

Expected installments are generated server-side from these rules. The backend prevents duplicate/overlapping active schedules for the same lease + category. Schedule create and update/activation transactions lock the parent lease row before checking conflicts. This parent-row lock serializes competing application writes for that lease, even when the candidate schedules are different rows.

The guarantee applies to writes through this service. Direct SQL or another service that writes schedule rows without taking the same parent lease lock can bypass the check; database administrators should restrict write access to the service role and route schedule changes through the API.

---

## Property expenses in this architecture

Property expenses are stored separately from lease schedules and tenant obligations.

Each expense records:

- asset hierarchy scope (`portfolio`, `site`, `building`, `unit`)
- category and description
- exact decimal amount and currency
- expense date
- recoverability flag (`recoverable` or `non_recoverable`)
- audit trail

Important product decision applied in M0.9-C2:

- recoverable expenses are **flagged for manual review**
- no automatic tenant allocation is created
- no automatic contractual recovery amount is calculated
- no invoice/payment records are created

This avoids silently inventing legal or contractual behaviour.

---

## Database changes and relationships

Migration `0003_service_charges_expenses.py` introduces:

- extension of rent schedule fields to support service-charge metadata
- tables/constraints for property expenses and property-expense audit events
- integrity checks for status/category enums and date ranges

Key relationship patterns:

- schedules remain linked to a lease and organisation
- expenses are organisation-scoped and linked to registry asset identifiers (portfolio/site/building/unit IDs), validated across service boundaries
- audit events are append-only records tied to their parent entity

---

## Financial precision approach

Financial values are handled as fixed decimal strings at API boundaries and `NUMERIC` in PostgreSQL.

Rules applied:

- validation enforces `^\d{1,12}\.\d{2}$` style money text
- no JavaScript floating-point arithmetic for stored financial values
- installment amounts must match schedule amount and currency exactly

This reduces rounding ambiguity and keeps calculations deterministic.

## Authentication vs authorization

### Authentication

The BFF reads the existing server-side session cookie and forwards short-lived bearer access tokens to backend services. Browser storage is not used for auth tokens.

### Authorization

Authorization is enforced in **both** layers:

1. **BFF layer** validates organisation-scoped inputs and same-origin write semantics.
2. **Lease Management backend** enforces role/permission checks and organisation ownership of leases and referenced assets.

This defense-in-depth model prevents UI-only restrictions from becoming security boundaries.

---

## API, BFF, and frontend interaction flow

1. User interacts with lease workspace UI (service-charge schedules and expense register).
2. Frontend calls authenticated Next.js API routes (BFF).
3. BFF validates request shape/scoping, forwards to Lease Management service, and validates upstream response shape.
4. Lease Management performs domain validation, permission checks, org isolation checks, and audit writes.
5. UI refreshes from returned canonical server state.

For write operations, idempotency keys are forwarded so retries do not create duplicate records.

---

## Why allocations are deferred

Allocation of shared costs requires contract-specific rules (area weighting, fixed splits, exclusions, caps, effective windows, rounding policy, dispute handling). M0.9-C2 intentionally avoids hard-coding these legal/business assumptions.

Current behaviour:

- expenses can be marked recoverable
- unresolved allocation context is captured via manual-review reasons
- operators decide recovery externally until allocation policy is productised
