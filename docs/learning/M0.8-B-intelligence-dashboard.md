# M0.8-B: Property Intelligence Dashboard

This dashboard is a learning and product demonstration. Its unit names, identifiers,
and source facts are synthetic. It does not read customer records or make a real
property, investment, or compliance recommendation.

## React components

A React component is a function that describes a part of the screen. In
`src/components/bow-era-intelligence-dashboard.tsx`, `IntelligenceDashboard`
returns the page, summary cards, controls, table, and assessment dialog. Smaller
components such as `PriorityBadge` keep repeated presentation consistent.

## Props and interfaces

Props are the values a parent gives to a component. For example,
`PriorityBadge` receives a `priority` prop whose type is the existing
`RiskSeverity` union (`'low' | 'medium' | 'high'`). TypeScript interfaces in
`src/lib/intelligence/risk-engine.ts` describe the input and output shape of the
domain engine; `IntelligenceAssessment` adds synthetic display labels around a
real `RiskAssessment` result.

These types help catch mismatched data while building. They do not validate
untrusted network input at runtime.

## React state

State is information that can change while someone uses a page. The dashboard
stores the search text, selected filters, and selected assessment with React's
`useState`. Updating one causes React to render the affected interface again.
The score itself is not UI state: it is calculated once for each fixture by the
domain engine.

## TanStack Table

TanStack Table is a headless table toolkit: it manages rows, sorting, filtering,
and pagination, while the application supplies the HTML and BOWERA styles.
`useReactTable` receives assessment objects, column definitions, and row-model
helpers. The table uses `assessment.unitId` as the row ID, so row identity does
not change when sorting or paging.

The global search checks synthetic unit/building names, unit identifiers, and
human-readable triggered indicators. Priority and completeness filters are
separate table filters. Sorting is available on data columns; the action column
is intentionally not sortable. Pagination displays five rows at a time.

## Radix UI

Radix Dialog provides accessible dialog behavior such as keyboard dismissal,
modal semantics, and focus management. The dashboard supplies the dialog title,
content, close controls, and visual styling. It does not implement custom focus
trapping.

The component tests use jsdom and React Testing Library to exercise actual
search, filters, sort, pagination, empty results, and dialog content. These are
automated component tests, not a browser-based visual or assistive-technology
audit. Manual browser testing at desktop, tablet, and mobile sizes remains
recommended.

## From deterministic algorithm to interface

`src/lib/intelligence/demo-assessments.ts` holds deliberately synthetic facts.
It calls the existing `assessPropertyRisk` function for every item, with a fixed
evaluation timestamp. It does not duplicate weights or calculate scores in
React.

For example, a fixture might indicate that a synthetic unit is vacant. The
engine then returns a `RiskAssessment` with the score, priority, rule IDs,
explanations, completeness, and timestamps. The UI formats those returned
values; it does not determine their meaning or adjust their weight.

The summary cards use `summarizeAssessments` to count the full fixture set.
Unknown facts stay `null`; the detail dialog lists missing fields and warns
that an incomplete score is not a low-risk conclusion. Already-expired leases
are shown as a separate warning because algorithm v1 does not score them.

Separating the domain calculation from presentation lets the algorithm be
tested and reused without rendering React, while the UI can change its layout
without silently changing risk policy.

## Authentication and data boundaries

The `/intelligence` page checks the existing server-side authenticated session
and redirects missing or expired sessions through the existing login route. It
does not accept an organization ID from the URL, call the Registry, or retrieve
real tenant data. This demo is not a production multi-tenant intelligence
service: any future real-data caller must authorize access to the organization
and unit before requesting or assessing their data.

## Practical exercise

Add one more clearly synthetic fixture with all facts known and no risk
indicators. Run `npm run test:intelligence-dashboard`, then open the assessment
details and verify that the displayed score, completeness, and explanations
come from the engine output. Do not edit the risk weights as part of this
exercise.

## Mini-test questions and answers

1. **Does TanStack Table decide what a high-risk score means?** No. The existing
   risk engine assigns priority; TanStack manages table interactions and row
   presentation.

2. **Why does the dashboard use a unit ID for the row key?** Unit IDs are stable
   identities. Array positions change when rows are sorted, filtered, or paged.

3. **What does `null` lease-expiry data mean here?** It means unknown. The UI
   reports incomplete data instead of treating it as zero days or inventing a
   value.

4. **Does the synthetic organization ID authorize access to customer data?** No.
   It is only a valid placeholder needed by the pure engine's input contract.
   The demo never uses it to retrieve data or establish authorization.

5. **What do the component tests prove?** They exercise the rendered component's
   interactions in jsdom. They do not prove visual quality in real browsers,
   production authentication integration, or screen-reader behavior with
   assistive technology.
