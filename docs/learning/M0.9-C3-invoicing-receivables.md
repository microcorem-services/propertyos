# M0.9-C3: Invoicing, Receivables & Payment Tracking

## Purpose and lifecycle

A rent or service-charge instalment is an **expected obligation** generated by a schedule. It is not an invoice. An authorised user selects eligible instalments when creating an invoice draft; other invoice lines may be entered manually. Property expense records remain separate and are not automatically recovered from tenants.

An invoice moves from `draft` to `issued`. Draft content can be edited. Issuance fixes the financial content: the API rejects later edits and PostgreSQL triggers prevent changes to issued invoice rows or lines. This milestone does not provide cancellation or credit notes, so an issued invoice cannot be corrected in place. A future correction workflow must be explicit.

Invoice numbers are supplied by an authorised user and are unique within an organisation. Currency must match the lease. The invoice total is the sum of line extensions; no tax fields, rates, VAT treatment, or tax calculations are included.

## Amounts and line calculation

Financial input and storage use decimal strings and PostgreSQL `NUMERIC`, not JavaScript floating-point arithmetic. Quantity may have up to three decimal places and unit amount up to two. The backend multiplies each quantity by its unit amount and rounds that line extension to two decimal places using half-up rounding; invoice subtotal and total are the sum of those rounded extensions.

The BFF validates decimal formats and line totals using integer cents. The interface displays the exact decimal strings returned by the service and does not calculate totals. The selected tax decision is to store entered amounts and their sum without determining or calculating tax.

## Receivables and arrears

An issued invoice contributes to receivables; a draft does not. Allocated payments reduce its outstanding balance. The service derives `due`, `overdue`, and `paid` from the invoice due date and balance. Invoice-list status filtering happens in the database before pagination.

The interface labels expected scheduled charges, issued invoices, outstanding balances, and manual payment records separately. Recording a payment does not verify that money reached a bank account. It is a user-entered record only.

## Database relationships and transactions

Migration `0004_invoices_receivables` adds:

- `invoices`, associated with a lease and organisation, with organisation-scoped invoice numbering.
- `invoice_lines`, including exact quantities and unit amounts, optional source-instalment references, and organisation-scoped uniqueness so a scheduled obligation cannot be reserved twice.
- Invoice audit events for creation, draft changes, and issuance.
- `payments`, with organisation-scoped idempotency keys and request fingerprints.
- `payment_allocations`, relating a payment to issued invoices, and payment audit events.

Invoice creation, line replacement, issue actions, payment creation, and allocations are committed transactionally. Issuance locks the invoice row. Payment allocation locks all target invoice rows in deterministic order before checking their outstanding balances, preventing concurrent application requests from allocating beyond the same balance. Repeated payment requests with the same idempotency key and payload return the existing payment; reusing that key with different data conflicts.

PostgreSQL triggers protect issued invoice content and lines against direct updates and deletes. Application authorization and locking do not protect against a privileged database writer bypassing the service. Restrict direct database write access to trusted migration/operations roles.

## Authorization and request flow

1. The browser sends same-origin requests to authenticated Next.js BFF routes. The session is held server-side; browser storage is not used for authentication tokens.
2. The BFF validates request shapes, decimal strings, response organisation identifiers, line totals, and payment allocation totals before forwarding requests.
3. The Lease Management API independently checks organization access and the read, create, or update permission required by each action.
4. The API validates lease and schedule references within the authorized organisation, performs changes in a database transaction, and records the actor in audit history.
5. The interface refreshes invoice, payment, and receivable data from the authenticated BFF after writes.

Payment allocations must use the invoice currency and cannot exceed either the submitted payment amount or the invoice's outstanding balance. A payment may be partly unallocated, but this milestone does not provide an endpoint for allocating the remainder later.

## Interface behavior

The invoice register is reachable from the Lease register. It supports status filtering, draft creation and editing, explicit scheduled-charge selection, issuance, overdue review, and recording a manual payment against the selected issued invoice. Create and update controls are permission-aware. Issued invoice content is displayed read-only.

The invoice number is entered by the user; automatic numbering, tax determination, cancellation, credit notes, payment gateways, bank verification, and automatic expense recovery are outside this milestone.
